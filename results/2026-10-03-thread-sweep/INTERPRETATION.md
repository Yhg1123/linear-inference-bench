# 增加线程不一定更快，小请求也不一定适合 GPU

本轮把旧的 batch 扫描扩展为线程 × batch 扫描：128 个配置、640 条按轮次记录、32,000 个单次计时样本。四种线程设置按预先确定的顺序 4→16→8→1 依次执行，五个相同种子 3010–3014，所有请求输入输出均为 CPU FP32，GPU 拷贝和转换已计入。没有并行运行问答测量。

## 本轮数据支持什么

**单条输入需要考虑传输成本。** batch=1 时，4/8/16 线程的 CPU INT8 中位数分别约 0.127 / 0.120 / 0.128 ms；对应 GPU FP16 约 0.150 / 0.154 / 0.174 ms。在线程数为 1 的组里，GPU FP16 约 0.148 ms、CPU INT8 约 0.159 ms，排名又不同。因此不能只按“batch=1”制定跨线程、跨机器的永久规则。

**中等以上批量更容易获得 GPU 收益。** 所有线程设置在 batch≥16 的中位数最快方案都是 GPU FP16。batch=128 时 GPU FP16 为 0.271–0.306 ms；CPU INT8 则为 0.501–2.303 ms，强烈依赖线程设置。此处的比较只是随机 TinyMLP 的 CPU 输入/输出请求。

**更多 CPU 线程不保证更快。** batch=128 的 CPU INT8，8 线程 0.501 ms，16 线程 0.720 ms，后者约慢 43.7%。CPU FP32 同样由约 2.020 ms 增至 2.656 ms。但五轮范围存在重叠，线程设置也不是跨时间完全交叉平衡，所以不能把“8 线程最优”推广到其他模型或所有机器。

## 误差与稳定性

CPU INT8 五个种子的最大相对 L2 误差随 batch 为约 0.0230–0.0296；本轮都满足选择器 0.03 的误差阈值。**这不等于真实问答正确率损失低于 3%**，也不能推翻此前 Qwen 动态 INT8 跑题的证据。

更快的中位数也可能带有较差的尾部。例如 batch=128，CPU INT8 8 线程中位数约 0.501 ms，最坏轮次 P95 为 1.043 ms；16 线程对应 0.720 / 1.787 ms。all_summary.csv 保留轮次范围、最坏 P95 和误差，不只提供最快一轮。

## 对实际应用的含义

这组数据适合用于“需要在本机运行某个 MLP 请求时，先挑哪些线程数、批量和精度进入候选测试”。它不证明完整问答能获得同等倍数加速。配套问答的 [432 次并发请求](https://github.com/Yhg1123/attention-kernel-lab/blob/main/results/2026-10-03-qa-load/INTERPRETATION.md)表明，当前多人等待主要受单推理线程排队影响；优化一个小线性层不能直接消除服务队列。
